run 页面属于**某一个仓库**：项目在 2026-09-27 同名重建过，旧 run 号只存在于归档库 `ColaMD-archive`，而归档库一旦删除就永久 404 —— 这份文件因此是那些结论唯一的长期出处，不要按"随时能重抓"来理解它。

生成方式：`python scripts/exportCiRuns.py`。脚本按文档里的 11 位号自动抓取，顺序是**当前库 → 归档库**；两边都取不到时**保留本文件里已有的那一行并标注"已不可达"**，绝不因为 404 就丢证据。

## 补录流程（2026-10-01 改为并入批次，不再独立成批）

**旧做法**：台账当成一个独立文档批次，每隔一段时间补一次。**这个做法已被证明是错的**——2026-10-01 一天之内因此落后三次（补到 #53 → 补到 #59 → 又缺 16 条），而这份文件的全部价值在于"run 号的唯一出处"，**一旦落后就等于不可信**。

**现行规则**：**每个 PR 在自己的批次里顺手补自己那几行。** 具体做法：

1. 合并一个 PR 之后，把该 PR 的 4 条 `pull_request` run 加上它那个 merge commit 的 2 条 `push` run 追加到下表（一行一条），并把头部 `run 总数` 刷新。
2. **取数一律 `gh run list --limit 60 --json headSha,event,conclusion,workflowName,databaseId` 实测，不靠记忆**；`total_count` 用 `gh api repos/TheQYQ/ColaMD/actions/runs?per_page=1` 取。
3. **按 `head_sha` 客户端过滤，不要用 `gh run list --branch`** —— 对 `pull_request` 事件的 `--branch` 过滤不可靠（#56/#57 那次它返回的是另一个 PR 的 run，见下）。
4. **`head_sha` 相同时必须再看 `event`** —— promote PR 的 head 就是 `develop` 的 tip，与上一个 merge commit 同值（PR #55 与 #54 那次）。
5. **`cancelled` 不等于 `failure`** —— 短间隔内连续合并两个 PR 时，后一个会吃掉前一个的 push 腿（已出现两次：`5b6684b` 与 `049c86c` 那对，第二次间隔仅 16 秒）。这类腿算"未验证"，不能算"已通过"。
6. 补录不必等 `develop` 的 push 腿跑完，但**要等它有结论**再写；未跑完就写等于把 pending 当成结论。

> **本批（#60–#62）就是按这条规则补的**：16 行，其中 `066c62c` 是 PR #60 的 head（后被 rebase 到 `752ce25` 重开为 PR #62，所以 **#60 的那 4 行与 #62 的那 4 行都留着**——它们是两次真实发生过的验证，不是重复记录）。
